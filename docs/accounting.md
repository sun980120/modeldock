# ModelDock 예산 정책

## 예산과 공급자 사용량의 구분

`daily_budgets`는 ModelDock 내부 접근 통제 장부입니다. `used_tokens`는 정산이 끝난 예산 차감, `reserved_tokens`는 진행 중 예약, `remaining=max(0, limit-used-reserved)`입니다. 공급자 청구서나 실제 잔여 할당량과 같은 숫자가 아닙니다. 예시 숫자나 컨텍스트 크기를 예산 잔고로 사용하지 않습니다.

사용자와 서비스 전체에 별도 한도를 적용합니다. 서비스 전체 값은 관리자 또는 공개 설정이 켜진 경우에만 응답합니다. 관리자가 한도를 기존 소비량보다 낮추면 잔여량은 0이 되지만 기존 장부를 수정하지 않습니다.

기간은 요청 시작 시점의 Asia/Seoul 날짜입니다. 초기화는 DB 일괄 reset 없이 날짜별 행으로 처리합니다. 한국 시간 자정 이후 새 요청은 새 날짜를 사용하고, 자정을 넘긴 기존 요청은 예약한 원래 날짜로 정산합니다. 활성 동시 생성 수는 날짜와 관계없이 계산합니다.

## 원자적 예약

모든 예산 변경은 `runtime_settings.id=1 SELECT ... FOR UPDATE`를 먼저 획득합니다. 동일 MariaDB를 사용하는 여러 애플리케이션 인스턴스에서도 사용자 상태·설정·예산·동시 생성 수를 한 트랜잭션으로 검사합니다. 사용자당 진행 중 요청은 1개입니다. 서비스 전체 동시 생성 상한도 따로 검사합니다.

대화 소유권을 확인하고 이전 완료 대화와 현재 질문을 합쳐 예약량을 계산합니다. 동일 `requestId`는 generation PK가 막으며 실패한 트랜잭션의 예약 증가도 롤백됩니다. 재시도에는 새 requestId와 새 예약이 필요합니다. 임의 자동 재생성은 하지 않습니다.

현재 상위 소스의 명시적 panel 최대 시도 4회와 judge 최대 시도 6회를 반영한 식입니다.

```text
I = UTF-8 대화 바이트 합 + 메시지당 64 + 1024
N = 참여 모델 수
O = 공통 최대 출력 토큰
예약 = N × 4 × (I + O)
     + 6 × (I + N × O × 4 + 4096 + O)
```

judge 입력에는 참여 답변 재입력과 합성 지시문을 포함합니다. 한국어를 일률적으로 글자 수/4로 환산하지 않습니다. tokenizer·상위 시스템 프롬프트·공급자 처리 방식이 달라 이 식도 절대적인 상한은 아닙니다. 대화는 100,000자 이하의 완료 이력만 허용하고 초과 시 새 대화를 요청합니다. 자동으로 문맥을 잘라 성공한 것처럼 처리하지 않습니다.

## 정산 상태

| 상태 | 의미 | 정책 |
| --- | --- | --- |
| CONFIRMED / 확정 | 모든 소비 호출의 확정 usage가 중복 없이 확인됨 | 향후 완전한 상위 장부 연동 시에만 사용. 현재 어댑터는 반환하지 않음 |
| ESTIMATED / 추정 | 완전한 호출 범위에 추정 tokenizer 등을 적용 | 향후 범위가 완전하게 확인될 때 사용. 현재 어댑터는 반환하지 않음 |
| PARTIAL / 일부 누락 | 상위 성공 합계가 있으나 실패·재시도 소비가 빠질 수 있음 | `max(예약, 상위 보고 usage)`를 예산 차감 |
| UNKNOWN / 확인 불가 | 사용할 수 있는 usage가 없음 | 예약 전체를 예산 차감 |

상위 `usage.total_tokens`는 성공 참여·합성의 합계로 한 번만 기록합니다. panel과 judge를 다시 더하지 않습니다. `reported_tokens`는 이 상위 보고값이며 확정 전체 소비라고 표시하지 않습니다. 개별 모델의 입력·출력 토큰이 없으면 제공하지 않습니다.

완료·실패·취소·타임아웃에서 현재 어댑터는 미확인 소비를 모두 환급하지 않습니다. DB에 입력한 `charged_tokens`와 `usage_quality`로 적용 정책을 감사할 수 있습니다. 이 때문에 실제 공급자 소비보다 내부 예산이 많이 차감될 수 있습니다. 관리자는 공급자 감사 자료 확인 후 **한도 조정**으로 이용 가능량을 조정하고, 원장 행을 수동으로 덮어쓰지 않습니다.

확정 전체 사용량을 얻을 수 있는 상위 API가 도입되면 개별 attempt ID 기반 원장을 추가하고, 완전성을 검증한 요청에서만 확정값으로 정산하고 차액을 환급하도록 변경해야 합니다. 현재 코드에는 완전성을 입증할 수 없는 응답을 확정으로 승격하는 경로가 없습니다.

## 초과·실패·복구

- 보고량이 예약보다 크면 실제 보고량 전체를 차감합니다. 잔여량은 0으로 표시하고 추가 예약을 거절합니다. 초과량을 버리지 않습니다.
- 중지 버튼은 DB 취소 플래그를 기록합니다. 작업 인스턴스가 최대 약 1초 안에 HTTP future와 응답 stream을 닫아 상위 API로 취소를 전파합니다. 공급자가 이미 처리한 소비는 취소로 사라지지 않습니다.
- 서버 종료·재시작·일시적인 DB 장애로 미정산 상태가 남으면 `expires_at`(전체 제한 시간+15초) 이후 스케줄러가 `INTERRUPTED`로 정산합니다. 여러 인스턴스의 복구가 경쟁해도 terminal 상태 재정산은 무시합니다.
- 완료와 취소가 경쟁하면 같은 DB lock 아래에서 먼저 확정된 terminal 상태를 따릅니다. 취소 플래그가 먼저 저장됐다면 완료 답변을 저장하지 않습니다.
- 대화 삭제 시 메시지는 물리 삭제하고 대화는 비공개 삭제 표식으로 숨깁니다. 소비 장부는 보존합니다. 활성 생성 중에는 삭제를 막고 중지를 안내합니다.

상위 게이트웨이가 취소 신호를 무시하거나 예약식 이상의 숨은 호출을 수행하면 공급자 비용이 내부 예상량보다 커질 수 있습니다. 금액 상한이 필요한 환경에서는 공급자별 결제 제한·키별 지출 제한도 함께 설정해야 합니다.
